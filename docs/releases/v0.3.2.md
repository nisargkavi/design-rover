# Design Rover 0.3.2

This patch addresses the correctness and safety findings from the independent audit of 0.3.1.

## Approved knowledge and storage

- Moving source comments or images no longer changes their decision identity solely because line numbers moved. Unambiguous legacy records retain their IDs, approvals and human notes during synchronization.
- Routine synchronization and bulk approval preserve protected removals. Accepting a removal of approved or human-annotated knowledge requires reviewing its specific change ID.
- Concurrent reviews compare the full prior model before saving. A stale reviewer receives a conflict instead of silently overwriting another decision.
- Interrupted saves leave a recovery journal. Clearing a stale lock does not make a partially installed model appear valid. Missing `system.json` also requires recovery when existing knowledge remains.
- Existing decisions can be explicitly revoked and reapproved, with accurate approval/rejection history. Shared metadata stores the repository root as `.`.

## Analysis and checks

- Local export lists and aliases are included in component discovery. Nested UI and feature-local import paths retain their real directories.
- Static Tailwind configuration extraction preserves nested token names. Context follows CSS-variable dependencies across recorded themes, and relevant component matches rank ahead of supporting token records.
- Confirmed changes to an explicitly approved component API can fail the default gate. Missing local generated snapshots no longer make an otherwise valid fresh checkout fail CI.
- Generated writes reject symlink paths outside the intended project boundary. CLI JSON errors and diagnostics also receive the audit's focused fixes.

## Contributions and releases

The release adds contribution guidance, issue forms and a PR template. Conventional Commit changes merged into `main` now enter a release pipeline that validates four Node/OS combinations before preparing the next version, notes and packaged CLI.

The workflow publishes to npm through OIDC trusted publishing, verifies and smoke-tests the registry download, publishes the scoped `@nisargkavi/design-rover` GitHub Packages mirror, and attaches the verified npm tarball and `SHA256SUMS` to a GitHub Release. An incomplete tagged release can resume through the Release workflow's `resume_version` input, with identity and content checks repeated. Maintainers configure npm trust and GitHub package visibility; the workflow's actual results establish publication status. See [development and release operations](../development.md#automated-releases).

## Validation

Local validation passed **196 library tests** and **32 release-script tests**, including Git-history scenarios, version preparation, release classification and artifact verification. All workspace typechecks and the fresh-project packaged CLI/MCP smoke check passed. The hosted release workflow repeats validation before publishing.

For an existing model, run `bunx design-rover@0.3.2 diff` and review the proposed changes before synchronizing. Incomplete external types, dynamic styling and CSS class contracts remain limitations; a clean check is not a complete design, accessibility or visual audit.
